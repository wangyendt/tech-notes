# Android 无障碍服务：控件树、手势与操作结果确认

当应用需要在用户明确发起的流程中辅助操作另一个界面时，首先要解决两个问题：当前界面有什么可操作对象，操作后是否达到了预期状态。Android 的 `AccessibilityService` 提供了观察界面和代用户执行操作的机制，但它不是通用的后台控制权限，也不会授予读取蓝牙 HCI 日志的能力。

无障碍服务的设计用途是辅助有障碍或暂时不便操作设备的用户。技术上能够执行某种操作，不等于产品可以不受限制地把它用作自动化接口；应说明用途、取得用户授权，并核查分发渠道的适用政策。[Android 无障碍服务指南](https://developer.android.com/guide/topics/ui/accessibility/service)

## 控件树不是截图，也不是应用的全部内部状态

系统通过无障碍事件通知服务界面发生了变化。服务可以查询 `AccessibilityNodeInfo` 节点，读取文字、内容描述、控件类型、可点击状态、屏幕边界等信息，再根据节点关系定位目标。

这与 OCR 的输入不同：OCR 从像素识别文字，无障碍服务使用界面暴露的语义结构。一个自绘控件可能看起来内容丰富，却没有提供足够的无障碍节点；反过来，节点也可能包含屏幕上没有直接绘制的内容描述。

| 能力 | 前提与局限 |
|---|---|
| 接收界面事件 | 由服务配置决定监听范围；事件不是完整的业务状态快照 |
| 查询窗口内容 | 需要声明 `canRetrieveWindowContent`，且目标内容实际对服务可见 |
| 查询多个交互窗口 | 还涉及窗口检索配置；不能假设当前根节点包含所有浮层 |
| 对节点执行操作 | 目标节点需要支持相应动作，且可能在执行前已失效 |
| 注入触摸手势 | 需要声明 `canPerformGestures`；坐标可能受布局或遮挡影响 |

这些配置声明的是服务能力，不代替用户启用服务。服务的连接和生命周期由系统管理；安装 APK 不等于服务已经运行。[AccessibilityService API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService)

## 三种输入方式解决不同问题

**节点动作**通过 `performAction()` 请求点击、滚动等语义操作。它不需要先计算触点，但不能假设所有自绘或嵌入式控件都正确实现了这些动作。

**触摸手势**通过 `dispatchGesture()` 提交点击或滑动路径。它适用于确实需要触摸输入的场景，但仍然受屏幕位置、窗口变化和用户同时操作的影响。

**全局动作**通过 `performGlobalAction()` 请求返回等系统操作。全局动作不能替代对目标应用内部业务状态的检查。[动作与手势接口](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService)

选择输入方式时，先确认目标语义和可用动作；需要坐标时重新读取边界，不复用上一次页面中的坐标。不要把“使用了控件树”写成“完全不受屏幕布局影响”。

## 操作已提交，不等于业务已完成

节点可能在页面切换后失效，手势提交前可能出现浮层，目标应用也可能因为网络或业务校验拒绝操作。动作返回成功或手势回调完成，都不能单独证明目标业务完成。

一个可检查的流程应把观察、输入和结果确认分开：

```text
用户发起并允许取消
  → 读取新鲜的窗口和节点
  → 确认目标唯一、窗口稳定、触点未被遮挡
  → 提交一次输入
  → 等待可辨认的业务状态变化
  → 已确认 / 未确认 / 超时 / 用户取消
```

这是工程设计建议，不是 Android 保证的原子操作。窗口检查与输入提交之间仍有竞态。对于开始运动、提交表单等不能盲目重复的操作，未确认时应停止后续输入，允许只读核对，而不是循环点击。

不应把空白控件树解释为“任务完成”，也不应把上一次留下的页面内容解释为本次操作成功。结果条件应来自目标业务，例如新计时持续前进，而不是仅仅看到一个相同标题。

## 无障碍、Shizuku 与蓝牙采集互不替代

无障碍授权允许服务使用相应的界面能力，不会把应用变成 ADB shell 或 root，也不会自动开放本机日志端口。需要辅助进程的系统调用时，应单独理解 [Shizuku 的工作原理与权限边界](../android-shizuku/README.md)；需要蓝牙包时，应检查 [HCI 日志及其读取出口](../android-bluetooth-hci-btsnoop/README.md)。

在[运动心率采集案例](../android-wearable-heart-rate/README.md)中，无障碍服务负责输入，Shizuku 只读 UI 桥负责窗口快照，状态机负责确认运动状态。这个组合是案例的实现选择，不是所有无障碍服务都需要 Shizuku。窗口 ID 过期、通知遮挡和短时锁屏的证据保留在案例中，不在这里扩展为全机型结论。

实际验证应分别覆盖用户启用与撤销授权、页面切换、节点缺失、浮层遮挡、超时及中途取消。只记录必要的状态与错误，不把完整窗口文字或截图默认保存为诊断材料。
