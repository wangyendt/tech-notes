# 在 Android 上采集可穿戴设备的心率数据

<p class="article-meta">Ye Wang · 2026-10-26 · Android / 蓝牙</p>

可穿戴设备的配套 App 能显示运动心率，但我希望在自己的 APK 中展示和保存这些数据。理想的操作是：在自己的界面点开始，自动进入某 App 的运动界面启动运动，再回到自己的界面；结束时做相反的操作，保存这段时间的心率和时间戳。

最后跑通的方案没有替换设备的蓝牙连接。配套 App 继续负责绑定和运动业务；原型用无障碍控制页面，通过 Shizuku 读取手机本机的蓝牙日志流。测试手机未 root，拔掉 USB 后可以独立采集。一次约三分钟的锁屏测试结束后，也读回了保存的记录。

本文隐去应用厂商、包名和设备型号，只保留实现方法与聚合统计。原始蓝牙日志、个人心率明细和绑定材料不公开。这个实现依赖测试手机的调试能力，并不是安装后就能适配任意 Android 手机的通用方案。

## 为什么保留配套 App 的连接

最初尝试过独立连接设备。原型发出的点测命令收到了 ACK，眼镜却没有测量提示，也没有返回心率。传输层能收发消息，距离完成绑定、业务握手和测量仍有一段距离。

其他尝试也各有问题：

| 尝试 | 本次结果 |
|---|---|
| 独立连接蓝牙 | 没有独立复现业务握手与绑定流程 |
| 使用导出的 IPC 接口 | 已测试的入口没有提供心率订阅 |
| 修改 APK，增加数据转发 | 重签后遇到启动和登录失败，维护成本高 |
| 把运动页移到虚拟屏读取 | 页面重建和后台渲染不稳定，未完成可靠性验证 |
| 保留原连接，读取本机蓝牙日志 | 测试手机存在可用日志流，能解析出运动记录 |

这些结果只针对本次测试的版本和接口。例如，没有找到可用 IPC，并不能证明其他版本也没有。考虑到目标只是获取运动期间的心率，继续复现整套设备协议并不划算，于是保留配套 App，分别实现页面控制和日志接收。

## 实现结构

![运动控制和日志接收的组件关系](assets/control-data-plane.svg)

原型有两条独立的工作链路：

- **运动控制**：无障碍服务执行导航和输入，Shizuku 的只读 UI 桥读取当前窗口控件，状态机检查运动是否真正开始或结束。
- **心率接收**：Shizuku 辅助进程连接本机日志流，解析目标业务消息，只把运动记录交给 APK，写入应用私有目录。确认结束后，接收器短暂收尾，再按本场时间范围生成 CSV 和统计。

两条链路分别报告状态。页面操作失败时，日志可能仍在接收；日志接收断开时，运动也可能还在继续。界面需要把这两种情况区分开。

### 权限与运行条件

Shizuku 让获授权的应用使用以 ADB shell 身份运行的辅助服务，不提供 root。本原型通过它读取窗口快照和本机日志流；无障碍服务负责用户发起的、可取消的页面输入。[Shizuku 设置手册](https://shizuku.rikka.app/zh-hans/guide/setup/)

当前实现要求辅助进程以 shell UID 运行。还没有单独测试普通应用 UID 能否直接读取这个端口，因此不能据此断言端口一定需要 Shizuku，也不能直接移除这项依赖。

运行前需要配套 App 已登录、设备已连接并佩戴，HCI 日志已启用，无障碍和 Shizuku 均已获用户授权。首次配置仍然需要调试设置。Android 11 及以上可使用无线调试在手机上配对和启动 Shizuku，无需一直连接电脑；非 root 模式下，手机重启后需要重新启动服务，服务停止不等于配对关系丢失。[无线启动流程](https://shizuku.rikka.app/zh-hans/guide/setup/)

## 从本机日志流提取心率

早期实现需要生成系统诊断包，再从中提取蓝牙日志。这个过程等待时间长，而且诊断包会包含其他系统信息。后来在测试手机上找到了 `127.0.0.1:8872` 的 btsnoop TCP 流，确认监听者是手机的蓝牙进程，而不是电脑上的转发代理，才改成流式接收。

AOSP 曾提供 `btsnoop_net` 实现，在特定构建和日志配置下通过本地 TCP 输出蓝牙日志。这是调试功能，不是 Android 面向第三方应用的稳定接口；打开 HCI 日志也不保证一定出现这个端口。[AOSP btsnoop_net 说明](https://android.googlesource.com/platform/system/bt/+/ea7ab70a711e642653dd5922b83aa04a53af9e0e/doc/btsnoop_net.md)

接收器只连接固定的 loopback 地址。建连后先检查 16 字节 btsnoop 文件头、版本和链路类型，再逐层重组：

```text
btsnoop 记录边界
  → HCI ACL 分片
  → L2CAP / CoC 重组
  → 业务协议帧、分片与校验
  → 目标事件
  → 运动记录字段与时间戳
```

TCP 的一次 `read()` 不对应一条记录：可能只有半个文件头，也可能包含多个包。每层解析器都要保留未完成的片段，并限制接收时长、字节数、包数和重组缓存。通过方向、通道、事件类别及负载结构校验后，才保存目标记录，不持久化整条蓝牙流。

完整诊断包仍可用于排障，但需要另行授权，不能在流式接收失败时自动生成。

### 中途接入时缺少通道协商

第一次接入日志流时，解析器收到有效帧，却没有输出运动记录。原因之一是监听开始得太晚：设备早已连接，前面的 L2CAP 通道协商没有录下来，解析器因此不认识后续业务通道。

用同一份录制做对照，严格依赖已观察协商的版本返回零条记录；加入有限的中途恢复后，能够提取目标记录。这个对照解释了该份录制的失败，不能用来解释此前所有零记录情况。

恢复方法是按已知入站帧形状筛选候选通道，再执行完整长度、分片、校验和业务结构检查，而不是在字节流中搜索一个像心率的数字。统计中也分别记录“已观察到协商”和“按帧结构推断”的通道，避免把推断当成已完成握手的证据。

## 开始和结束为什么会不稳定

页面控制没有优先使用 OCR，而是根据控件文字、类、可见性、边界和相邻结构确定唯一目标。但有些控件最终仍要通过中心坐标触控，不能认为用了控件树就完全不受窗口变化影响。

### 嵌入页面的窗口 ID 过期

某些页面中，原生根窗口已经更新，嵌入式子节点却仍报告旧窗口 ID。继续按子节点的 ID 查询，得到的树就可能残缺或为空。

修复后，查询始终路由到当前配套 App 的根窗口，同时验证节点身份、窗口稳定性和快照时效，不复用之前成功过的窗口 ID。

### 通知遮住了目标控件

另一次故障中，目标控件定位正确，但通知浮层恰好盖住顶部标签，触控打开了通知。只检查配套 App 是否有焦点还不够：通知可以不获取焦点，却覆盖点击位置。

输入前需要重新检查窗口层级、焦点和目标区域的遮挡。发现遮挡就停止，等待用户处理，不自动点开或关闭通知。检查与触控提交并非原子操作，仍存在竞态；所以未观察到预期结果时必须记为“未确认”，不能盲目重试。

### 用页面变化确认结果

原型采用有超时和取消入口的状态机，不按固定延迟连续点击。

| 观察结果 | 处理 |
|---|---|
| 发送 GO 之前失败 | 标记未发送开始操作，排除问题后可重试 |
| 已发送 GO，但没有新运动计时前进 | 标记开始未确认，禁用重复开始，允许只读核对 |
| 新运动页出现，且计时继续前进 | 确认运动开始 |
| 已点击暂停或结束 | 继续等待明确结束态，不立即结束本地场次 |
| 出现明确结束提示，或稳定回到可启动页且无进行中面板 | 确认运动结束 |
| 结束未确认 | 保留本地场次，不写入虚假的结束时间 |
| 用户手动切回原型 | 取消后续输入，展示当前状态和可用操作 |
| 控件读取或整个流程超时 | 停止输入，保存错误，尝试返回原型 |

空白控件树不算结束证据，静止的旧计时也不算新运动。GPS 相关提示归入可识别的错误，但不能统一解释为“权限未授权”：定位开关、信号和 App 自身的判断都可能影响启动。

即使锁屏或系统策略阻止自动返回，错误也要保留到用户下次打开原型时显示，不能一直停在“操作中”。

## 时间戳和数据质量

保存记录时，首先要分清三个时间：

| 时间 | 来源 | 含义 |
|---|---|---|
| 设备记录时间 | 业务负载 | 设备给出的采样或记录时刻 |
| HCI 时间 | 蓝牙日志 | 传输记录的日志时间 |
| APK 处理时间 | 应用回调或落盘 | 手机实际处理该记录的时刻 |

当前 CSV 中的 `arrivalUnixMs` 来自 **HCI 时间**，并不是 APK 回调时间。这个命名需要修改；在修改前，分析脚本必须按实际含义使用它，不能据此证明锁屏时 APK 正在逐条执行。

本场记录按“手机发送开始命令至确认结束”的时间窗口筛选。设备时钟和手机时钟没有独立对齐，也没有匹配配套 App 的运动记录 ID，因此这个窗口只是实用的关联方式，不是精确的会话认证。

### 零值和长间隔

原始零值保留在记录中，图表在该处断线，不用上一条正常值填充。零值不表示实际心率为零。重复时间戳也保留，不静默去重。

两场独立测试得到以下聚合结果。它们的持续时间和操作条件不同，不是同一场运动中新旧实现的性能对照。

| 测试 | 原始记录 | 非零记录 | 原始零值 | 正间隔中位数 | 最大记录间隔 |
|---|---:|---:|---:|---:|---:|
| 亮屏，手机内完成开始、采集和结束 | 95 | 77 | 18 | 1.004 秒 | 4.123 秒 |
| 拔掉 USB，用户锁屏约三分钟后结束 | 158 | 138 | 20 | 1.010 秒 | 7.093 秒 |

两场的零值都集中在开头。后一场有 5 个超过 3.030 秒的记录间隔，不能因为中位数接近一秒，就称为严格 1 Hz。最大间隔两端记录的 HCI 时间相同，具有同批上报的特征，但这不足以判断间隔来自设备、蓝牙、系统省电还是解析链路。

锁屏由用户现场操作并报告，结束后 CSV 已读回核对。测试没有记录精确的锁屏、解锁时刻，也没有同时覆盖全链路的独立原始流。因此，目前验证的是本机短时锁屏后可以得到记录，尚不能证明长期稳定、没有丢点或具有医疗准确性。

质量检查使用下面的长间隔提示规则：

$$
\Delta t_i=t_i-t_{i-1},\qquad
\tau=\max\bigl(3\,\mathrm{s},\;3\,\mathrm{median}(\Delta t_i>0)\bigr).
$$

这是排查用的阈值，不是协议规定，也不能直接换算成丢包率。[质量检查示例](examples/quality_check.py) 使用合成输入，分别统计零值、重复时间戳和正间隔，不插值、不补点。

## 换一台手机需要验证什么

迁移不能只检查 APK 能否安装。至少要完成以下测试：

1. 配套 App 已登录，设备已佩戴并连接。
2. 启用 HCI 日志后，本机日志端口存在；授权进程能读取有效帧，而不只是成功建立 socket。
3. 运动消息能通过方向、通道和负载结构校验。
4. 控件树和窗口查询仍有效，开始、结束的业务状态都能确认。
5. 无障碍和 Shizuku 已获授权，后台策略允许接收器运行。
6. 分别验证拔线采集、锁屏、结束保存，以及重启后恢复。

本次无线配对时，输入通知曾位于通知列表下方；最初只显示搜索服务，允许后台运行并重启搜索流程后才出现配对码入口。因为两项操作同时发生，不能确定省电策略是唯一原因。排障时应先区分服务没有启动、没有发现配对服务和配对关系失效，不必一律删除配对重来。

一个安装包可以引导安装依赖，但不能静默获得无障碍权限、调试权限或 shell 身份。验证无线启动后，再拔掉 USB 完成一次采集，才算确认手机独立运行，不能用电脑启动脚本成功来替代。

下一轮测试需要补充 APK 处理时间和锁屏标记，对同一场运动记录独立来源的对照，再增加测试时长和机型。目前的原型已能在测试手机上使用，跨机型适配和长时间采集还需要这些验证。
